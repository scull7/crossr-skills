## why
Without mechanical gates, public surfaces will drift again after the next skill add.

## scope_in
- Parse `docs/public-skills.json` in `scripts/verify-docs` (schema from T-1)
- Fail if any allowlisted skill lacks non-empty SKILL.md
- Fail if README table skill names ≠ allowlist
- Fail if book catalog table skill names ≠ allowlist (catalog present after T-3)
- Fail if stub names in `out` / known stubs appear as marketed skills on public surfaces (site/, book/src/, README.md)
- Fail if overview promises TOC skill docs while SUMMARY has zero skill children
- If book/README mention AVRIL/AXEL, require HARNESS-SPEC §12/§13 headings
- HTML report status badge and body driven by real failure state (no hardcoded PASS)
- **Site skill count/pill equality: NOT enabled in this PBI** — implemented behind a flag or deferred entirely to T-5 so main is not forced red by pre-existing marketing drift
- Document in script header: site enforcement lands with marketing PBI (T-5)

## scope_out
- Rewriting marketing narrative (T-5)
- Enabling site pill/count FAIL on stale homepage (T-5)
- New book chapters
- Changing allowlist membership

## acceptance_criteria
- [ ] Removing one allowlist skill from README causes docs-verify FAIL
- [ ] Adding a vapor skill name to book catalog causes FAIL
- [ ] Mentioning a stub dir name as a skill in README causes FAIL
- [ ] HTML report shows FAIL when checks fail and PASS only when all pass
- [ ] `just docs-verify` exit code matches report status
- [ ] Allowlist integrity check runs every time
- [ ] After this PBI alone (before T-5), docs-verify can PASS on main without requiring site pill rewrite
- [ ] Script or README notes that site catalog enforcement is T-5
